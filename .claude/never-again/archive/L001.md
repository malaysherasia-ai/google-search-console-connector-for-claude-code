# L001 — scripted edits must fail loudly

**Symptom:** Demo mode showed "Not connected to Google Search Console" in the dashboard. Earlier, a multi-file Python edit crashed halfway with UnicodeDecodeError ('charmap' codec, byte 0x9d).

**Cause:** Edits were applied with Python `str.replace` inside Bash heredocs. When the target text had shifted (a telemetry route had been inserted between the two lines being matched in `src/app-server.ts`), `replace` matched nothing and returned the string unchanged, so `/api/sites` never got its demo branch. Separately, `open()` without `encoding=` uses cp1252 on Windows; files containing UTF-8 punctuation (curly quotes, en dashes) fail to decode, aborting the script after some files were already written.

**Rule:** In scripted edits, assert each old string matches exactly once (`assert s.count(old) == 1`) and read/write with `encoding='utf-8'`.

**Fix:** Wired the demo branch with the Edit tool; later scripts use a `rep()` helper that asserts a unique match.

**What would have gone red:** nothing at edit time; `tsc` passed because the unmodified code was valid. Only the screenshot review caught it.

**Hook candidate:** a PreToolUse(Bash) check that warns on inline Python calling `open(` without `encoding=`. Needs its own settings entry (non-commit trigger); propose if this recurs.

**Sharpened (same session):** Python text-mode writes on Windows also converted LF files to CRLF, which then broke later exact-match edits. Use `newline=''` on both read and write. Added `.gitattributes` (eol=lf).
